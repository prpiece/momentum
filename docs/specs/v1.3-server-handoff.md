# v1.3 server hand-off (Track B → Track C)

Track B adds no Supabase migrations (docs/specs/README.md). This lists what the server needs for v1.3's synced data, for Track C's first migration.

The server keeps one jsonb `data` object per synced row (`public.sync_rows`), merged field by field, so new **columns** on a synced table need no server change. New **tables** do.

## Must add

| What | Change | Why |
|---|---|---|
| `sync_rows.tbl` check | add `'calendar_subscriptions'` to the allowed values (migration `20261110083515_sync.sql`, the `tbl in (...)` check) | v1.3 syncs calendar subscriptions (name, url, colour, order) so the phone shows subscribed events with their calendar. Without it every subscription push is refused. |

## Optional (if Track C adds field checks later)

- `calendar_subscriptions.url` is a private calendar address (Google's secret iCal link). It is protected by the existing RLS (owner only) like every other row; do not expose it in any shared or friend-visible view.
- Habit goals gain `period: "day" | "week"` inside the existing `habits.goal` JSON text; nothing to change.

## Old phone builds (D257)

An older app drops fields it doesn't know only locally: it pushes changed fields only, so the server keeps `deadline`, `duration_min`, `someday`, `waiting` and `subscription_id` set by a newer device. Nothing on the server should rewrite whole rows.
