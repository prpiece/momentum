# Tickets: v1.2 iOS and Android (Expo companion)

Built from [v1.2-mobile.md](v1.2-mobile.md) (D229, ADR 0006). Work one ticket at a time, in the order below.

**Status (2026-11-12, D246–D250):** C1–C10 were built before any design ticket ran. v1.2.0 ships that UI with fixes only (D248). D1–D6 now run as a redesign starting from the built app, and R1 builds the result for one v1.2.x.

## How to work these tickets

- **Design tickets (`D*`) run with `/ai-mobile-product-design-director`.**
  - This is a new native app, so run the skill's full gates: brief, journeys and states, research, system, wireframes, final, handoff.
  - Treat the desktop app and its existing phone web layout (D200) as the brand and content source to learn from, not as screens to port.
  - Each gate ends with your approval before the next starts. No final visuals before wireframes are approved.
  - Every deliverable passes the skill's anti-slop gate (`references/mobile-anti-slop.md`).
  - Outputs go to `docs/design/mobile/`.
- **Code tickets (`C*`) run with `/ponytail:ponytail`.**
  - Before writing code, climb the ladder and put the answer in the PR: does it need to exist, is it already in `src/domain` or the stores, does Expo or React Native cover it, is it already installed?
  - Each ticket's **Ladder notes** give the expected answer; challenge them if the code says otherwise.
  - Smallest diff; one check for every piece of real logic.
  - Follow CLAUDE.md: pure logic in `src/domain/` with a test beside it, decisions in PLAN.md, one commit per ticket, files staged by explicit path.
- **Ops tickets (`O*`) are yours:** accounts, payments, consoles, testers. Claude can prepare text and checklists but can't sign up, pay or accept agreements.
- **A screen ticket waits for its design ticket.** A code ticket that builds a screen starts only after the design ticket under **Waits for** is approved.
- **Done means verified:** on the Android emulator at least, and on an iPhone via TestFlight for anything with touch, the keyboard or notifications.

## Timing

## Code (`/ponytail:ponytail`)

### C1 Expo shell that runs the shared domain
- Create `mobile/` with `create-expo-app` (TypeScript, Expo Router).
- **Metro:** `watchFolders` includes the repo root, and a path alias reaches `src/`.
- **Prove the sharing works:**
  - one screen imports `parseQuickAdd` (or the current quick-add entry point) from `src/domain/quickAdd.ts`;
  - it shows the result for a typed string;
  - it runs in a development build on the Android emulator (`npx expo run:android`).
- Record which shared dependencies need anything under Hermes: chrono-node, rrule, ical.js and `Intl` date formatting. Note any polyfill in PLAN §4.
- **Ladder notes:**
  - no monorepo tool (Nx, Turborepo) and no npm workspaces unless Metro can't resolve without them;
  - no moving or copying of `src/domain`.
- **Check:** a test (in `mobile/`) that imports a domain function, so a domain change that breaks React Native fails CI.
- **Done:** the development build runs on the emulator and shows a parsed quick-add result.

### C2 Shared core: a pluggable database driver
- **`src/db/client.ts`** exports a `Driver` type (`select`, `execute`, `transact`) and `setDriver()`. Desktop sets the Tauri SQL driver at startup, so its behaviour is unchanged.
- The write chain, `onWrite` and `onWriteError` stay in `client.ts`, so both apps get the same ordering.
- **Move UI side effects out of the stores:**
  - `toast` (sonner) and `withTransition` become callbacks the app registers;
  - `derive` moves from `features/tasks/selectors.ts` into a pure module, with the React hook staying in features.
- **Sync engine:** `src/lib/sync/engine.ts` goes through the driver instead of `@tauri-apps/plugin-sql` types. It gets the Supabase client and the secret store from the app, so desktop keeps the keychain commands and the phone uses `expo-secure-store`.
- **Ladder notes:**
  - one interface with exactly two implementations (desktop and phone), which ponytail allows because both exist;
  - no ORM and no repository rewrite: the SQL stays as written.
- **Check:**
  - `npm test` and `npm run test:server` unchanged;
  - a desktop sync round trip with the sync-test identifier (as in v1.1);
  - `lint:selectors` still passes;
  - a CI grep check fails if `src/domain`, `src/db`, `src/stores` or `src/lib/sync` import `@tauri-apps`, `react-dom`, `sonner` or DOM globals. This encodes the boundary.
- **Done:** desktop unchanged; the shared folders import nothing desktop-only.

### C3 Phone database
- `expo-sqlite` driver implementing C2's `Driver`.
- **Migrations:** apply `src-tauri/migrations/*.sql` in order, tracked with `PRAGMA user_version`, inside one transaction per file.
- **Bundling the SQL:** a script (`scripts/`) generates a TS module with the SQL strings, or a Metro raw-text transformer is used, whichever is smaller. CI checks that the generated file matches the source.
- **Check:** a test runs every migration on an empty database and then compares the schema (`sqlite_master`) with desktop's after the same migrations. `node:sqlite` is already used in `src/db` tests.
- **Ladder notes:** don't re-author the schema; the same files run everywhere.
- **Done:** the phone opens a migrated database, the stores hydrate, a task saves and survives an app restart.

### C11 Delete account and the 30-day content purge
- **Server** (`supabase/migrations/`):
  - a `deletion_requested_at` column on `profiles`;
  - RPCs to request and to cancel deletion;
  - a `pg_cron` job that, after 7 days, hard-deletes the owner's rows and the auth user;
  - the same job clears content from tombstones older than 30 days, keeping `{id, deleted_at}`.
- Signing out every device needs the service role, so it runs in that job or in one Edge Function, never in an app.
- **Server tests:** request then cancel; the purge keeps tombstones; another account can't delete yours.
- **Apps:**
  - phone: Settings → Account → Delete account (per D5), with the cancel banner on sign-in in the grace period;
  - desktop: the same button. Small, and the Terms promise it.
- **Web:** `site/delete-account.html`.
- **Ladder notes:** `pg_cron` and the existing security-definer pattern; one job does both deletions.
- **Done:** a deletion from the phone completes after the grace period, and the desktop is signed out cleanly.
