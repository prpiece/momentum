# Spec: v1.4 Sharing

Phase C, which ships after social (D181). Decisions: D126, D129–D142, D153–D157. ADR 0004. Depends on v1.1 sync and the v1.2 friends graph (inviting friends is the easy path).

## Goal

Small groups work together on lists and folders. For example, you share a "Momentum" folder with @dalba0, and an API developer joins only the API list. Each member keeps their own reminders, tags and pins, and nobody can see or change anything their role doesn't allow.

## Out of scope

- Sharing habits, events or countdowns.
- Workspaces, admins and per-seat billing (D183).
- Comments and chat.
- Push notifications for edits.
- Live presence such as "Sam is viewing".

## Model

- **Share**: a list or folder that more than one account can see (see the glossary).
- **Membership:** `share_members(container_type: 'folder'|'list', container_id, account_id, role: 'owner'|'editor'|'viewer', added_at, added_by)`.
- **Access is additive** (ADR 0004). An account's role on a list is the highest of:
  - its direct membership on that list, and
  - its membership on each shared folder above the list (at most 3 levels).
- **The owner** is the owner of the outermost shared folder, or of the list when it's shared on its own. The owner manages membership at every level (D153).
- **Rows inside shares:** every list, section, task and attachment row in a share has `owner_id` set to the share owner. `created_by` and `completed_by` record who acted.
- **One SQL function, `can_access(list_id, min_role)`,** walks the folder chain and backs every RLS policy and storage policy.
- **The member cap** counts distinct accounts across the whole tree under the top shared folder, owner included: 3 on the free plan and 25 with Supporter. The server enforces it when adding a member.

## The personal layer (D132)

- **Shared on a task:** title, note, status, priority, schedule, recurrence, section, checklist, subtasks, attachments and assignee.
- **Personal:** stored in `task_personal(task_id, account_id, reminders, tags, pinned)` and `container_placement(container, account_id, folder_id, sort_order)`.
- **Focus sessions** are already per account.
- **Locally,** the store merges the personal row into the `Task` it shows. Edits to personal fields write `task_personal`, never the task.
- **Tags on shared tasks** live only in the personal layer. Your tag list never fills up with collaborators' tags.
- **Matrix quadrant:** computed from the shared priority and due date, so every member sees the same quadrant.

## Sidebar placement (D140, D153)

- **Shared folders** always sit at the top level of each member's sidebar, ordered per member.
- **A shared list** can go into one of your personal folders.
- **A list-only member** sees the list on its own, with the hint "in Momentum · @owner". They never see the folder or its other lists.

## Roles

| Action | Owner | Editor | Viewer |
|---|---|---|---|
| See the contents | ✓ | ✓ | ✓ |
| Create, edit, complete, delete and move tasks within the share | ✓ | ✓ | |
| Create and rename lists and sections inside a shared folder | ✓ | ✓ | |
| Be the assignee | ✓ | ✓ | |
| Use the personal layer (reminders, tags, pins, focus) | ✓ | ✓ | ✓ |
| Invite and remove members, change roles | ✓ | | |
| Move a list out of the share, rename or delete the share | ✓ | | |
| Leave | after transferring ownership | ✓ | ✓ |

Triggers enforce this on the server (D155). The client only hides the controls.

## Invites (D131)

- **By @handle:** creates a pending membership that the invitee accepts or declines. A blocked account can't invite you.
- **By link:**
  - `momentum://share/<code>`, which uses the same web redirect as friend invite links.
  - Valid for 7 days. Only the owner can revoke it.
  - The link records which role it grants.
  - The owner sees who joined through it.
- **Limits:** 20 invites a day, and the member cap is checked when the invite is accepted.

## Moving across the boundary (D135, D141, D153)

- **Moving a task into a share** asks for confirmation the first time ("Members of Momentum will see this task, its note and images").
  - Subtasks move with it.
  - Personal tags and reminders move into `task_personal`.
- **Moving a task out of a share** removes it for everyone else. Only the task's creator or the owner can do it.
- **Moving a personal list into a shared folder** shares the list. The confirmation names everyone who gains access.
- **Moving a list out of a shared folder** is owner-only.
  - The list keeps its direct members.
  - Folder-only members lose access.
- **Moving a list that already has its own members into a shared folder** is allowed only when the same account owns both.
- **A personal folder can't move into a shared folder.**

## Losing access (D136, D153)

- **Leaving or being removed:**
  - The share's rows are purged from that member's devices on their next pull. The server sends a membership tombstone.
  - Any of their assigned tasks are unassigned.
  - Their `task_personal` and `container_placement` rows for the share are deleted.
  - Nothing is kept as a copy.
- **The owner leaves:** they must transfer ownership first. Otherwise the share is deleted for everyone, after a warning that names everyone affected.
- **The owner deletes their account:**
  - Ownership passes to the longest-standing editor, or failing that the longest-standing viewer.
  - If there are no other members, the share is deleted.
- **A member deletes their account:** they're removed, and their completions show as "Deleted user".
- **Attachments** count against the uploader's quota and move to the owner's when the uploader deletes their account (D137).

## Assignee (D133)

- **`tasks.assignee_id`** is nullable and must refer to a current member who is an editor or the owner.
- **Today and Upcoming** show your own tasks plus shared tasks assigned to you or to nobody.
- **Each list's filter bar** gets an "Assigned to me" filter.

## Activity and awareness (D138)

- **The `task_activity` row** gains `actor_id`.
- **The task drawer** shows an Activity tab ("@sam completed this · 2h").
- **The sidebar** shows an unread dot on a shared list when a new activity row from someone else arrives. `share_reads(account, container, last_seen_version)` stores the read position.

## Content safety (D156–D157)

- **Notes** render with no raw HTML, which is how they render today. Links open in the system browser.
- **Only `attachment:` images render.** Remote image URLs in notes become plain links.
- **Uploads:**
  - PNG, JPG, GIF and WebP are allowed. SVG is refused.
  - The type is checked from the file's magic bytes, both on the client and in a storage hook.
  - EXIF and other metadata are stripped on the client before upload.
- **Attachment storage** is a private bucket with the path `share/<share_id>/<uuid>.<ext>` and signed URLs that expire after 1 hour. The storage policy calls `can_access()`.
- **Local attachment files** are downloaded when first viewed and cached in `attachments/`. They're evicted when access is lost.

## Sync changes

- **Pull** returns rows where `can_access(list, 'viewer')` is true, plus the account's own rows.
- **Membership changes** bump a version on every row in the affected share, so new members get the backfill through the normal pull, and removed members get tombstones.
- **Push** checks the role per patch on the server. A refused patch shows up in Sync issues (v1.1) with a reason such as "You're a viewer in Momentum".

## Edge cases

- **An editor's offline edits arrive after they were demoted to viewer:** the patches are refused. The task reverts on the next pull, and Sync issues explains why.
- **Two editors move the same task to different lists while offline:** the later arrival wins, the same as any field.
- **A task moved out of a share while another member was offline editing it:** that member's patch is refused, because they lost access.
- **A recurring shared task completed by two members at once:** both write the same deterministic occurrence id. The first `completed_by` stays, because it's immutable once set.
- **The cap is reached while a link is outstanding:** accepting fails with "Momentum is full", and the owner is told.
- **A blocked user is in the same share:** they stay, and blocking doesn't remove members (D150).
- **A share owner has Supporter (cap 25) and then cancels it:** existing members stay, and new invites are refused until the share is under the cap.

## Verification

- **RLS and storage suite** (D154), run against the "Momentum" fixture: an owner, a folder editor, a folder viewer, a list-only API dev, a stranger and a blocked user.
  - The suite checks every table and bucket operation against the role table.
  - The API dev must not see the folder, its other lists or their attachments.
- **The sync simulation** gains membership changes, role changes and moves across the boundary.
- **Real-app check:** three accounts share the folder. The list-only member sees only API. A viewer's attempted edit is blocked in the UI and refused by the server.

## Acceptance

- Every row in the role table is covered by a passing RLS test.
- No path lets a member see content outside what they can access, including attachments.
- Personal tags, reminders and pins never leak to other members.
