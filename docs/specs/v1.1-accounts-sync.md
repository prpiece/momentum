# Spec: v1.1 Accounts and sync

Phase B. Decisions: D105–D107, D109, D115–D124, D127–D128, D154–D162. ADRs 0001, 0002, 0005.

## Goal

A user can create an account, sign in on several devices, and see the same data on all of them. Edits made offline merge without losing data. Someone who never signs in notices nothing new except an Account section in Settings.

## Out of scope

Sharing (v1.3), friends and leaderboards (v1.2), payments, AI, a web client and mobile builds. The server schema still leaves room for them: every row has an `owner_id`, and lists have an optional share reference added in v1.3.

## Accounts

- **Sign-in methods:** an email one-time code (6 digits, typed into the app), Google, or Apple. There are no passwords.
- **Desktop OAuth flow:**
  - PKCE runs in the system browser.
  - The callback comes back through the `momentum://auth` deep link (`tauri-plugin-deep-link`).
  - If the deep link can't be registered, it falls back to a loopback port.
- **First sign-in:**
  1. Ask for an @handle: 3–20 characters from `a-z0-9_`, unique. Reserved and profane words are refused by a server check. The handle can be changed every 30 days.
  2. Ask for a display name.
  3. The avatar is the user's initials or one of the presets.
- **Age:** a checkbox confirms the user is 13 or older and accepts the Terms and Privacy policy, both linked. Sign-up without it is refused.
- **Token storage:**
  - The refresh token lives in the OS keychain (`keyring` crate behind a Tauri command).
  - The access token lives only in memory.
- **Settings → Account shows:**
  - the handle, display name, avatar and email;
  - signed-in devices (name, platform, last seen);
  - Sign out;
  - Sign out everywhere;
  - Export data (the existing zip);
  - Delete account.
- **Account deletion:**
  - Every device is signed out immediately.
  - Rows are hard-deleted after a 7-day grace period.
  - Signing in during the grace period cancels the deletion and shows a banner.
  - Each device then shows the sign-out prompt below.

## What syncs

| Synced (per account) | Per device (never synced) |
|---|---|
| folders, lists, sections, tags, tasks, task_activity, calendar_events (including countdowns), habit_groups, habits, habit_checkins, focus_sessions, rest_days, celebrations, user settings, Getting started progress | layout and bar position, density, font size, window bounds, hotkeys, microphone, voice model, notifications on/off, mini window state, `reminder_log` fire records |

- The settings JSON (one SQLite row, `domain/settings.ts`) is split into `userSettings` (synced) and `deviceSettings` (local):
  - **User:** `theme`, `accent`, `defaultView`, `weekStart`, `timeFormat`, `smartParse`, `viewOptions`, `savedFilters`, `calendar`, `matrix`, `matrixColors`, `pomodoro`, `sounds`, `onboarded` and `gettingStarted`.
  - **Device:** `density`, `motion`, `fontSize`, `zoom`, `layout`, `barPosition`, `sidebarSide`, `sidebarCollapsed`, `sidebarMoreOpen`, `closeToTray`, `launchAtStartup`, `checkUpdates`, `notify`, `quickAddShortcut`, `miniShortcut`, `voiceShortcut` and `voiceMic`.
  - **Not settings:** the What's new seen-version stays in localStorage, as it is now.
- **Reminders:**
  - Every running device fires a reminder.
  - Dismissing or snoozing it writes a synced `reminder_state` row, keyed by the reminder key, that holds `dismissed_at` and `snooze_until`.
  - Other devices honour that row on their next pull.
- **Focus:** a running focus timer is never synced. Only the finished `focus_sessions` row is.

## Local schema changes (migration `0009_sync.sql`, after v1.0's migrations)

- **New columns on every synced table:**
  - `updated_at` and `deleted_at`, where the table doesn't already have them;
  - `server_version INTEGER` (null means never synced).
- **Inbox:**
  - `lists` gets `kind TEXT NOT NULL DEFAULT 'normal' CHECK (kind IN ('normal','inbox'))`.
  - The `inbox` row gets a new UUID with `kind='inbox'`, and every reference is rewritten in the same migration.
  - Code finds the inbox by `kind`, never by id.
- **Tags:** `tags` loses `UNIQUE` on `name` and gains a unique index on `(name COLLATE NOCASE) WHERE deleted_at IS NULL`.
- **Activity:** `task_activity` gets an `id TEXT` UUID. The table is rebuilt because SQLite can't change a primary key in place.
- **Natural-key tables:**
  - `habit_checkins (habit_id, date)`, `rest_days (date)` and `celebrations (key)` keep their natural keys.
  - On the server, the key gains `owner_id`.
- **Count-goal check-ins** add `delta REAL NOT NULL DEFAULT 0`. This is the unsynced local increment since the last push.
- **New sync tables:**
  - `sync_outbox(seq INTEGER PRIMARY KEY, tbl TEXT, row_id TEXT, fields TEXT, created_at TEXT)`;
  - `sync_state(key TEXT PRIMARY KEY, value TEXT)`, which holds the cursor, the account id and the minimum schema.
- **Hard deletes become soft deletes:** every remaining hard `DELETE` in `src/db/repo.ts` turns into setting `deleted_at`.
  - Trash is emptied after 30 days, not at launch (`repo.ts:33`).
  - Rows are purged locally only once their tombstone has been pushed.

## Server schema (Supabase, `supabase/migrations/`)

- **Every table:**
  - It mirrors its local table and adds `owner_id uuid NOT NULL REFERENCES auth.users`, `version bigint NOT NULL` (from one global sequence) and `updated_at timestamptz` (set by the server).
  - It has RLS enabled with the policy `owner_id = auth.uid()` for now. v1.3 replaces this with `can_access()`.
- **`profiles`:** `id`, `handle` (unique, citext), `display_name`, `avatar`, `handle_changed_at`, `deleted_at`.
- **`devices`:** `id`, `owner_id`, `name`, `platform`, `last_seen`.
- **`server_meta`:** `min_client_schema int`.
- **`usage_counters`:** `owner_id`, `kind`, `period`, `count`. These exist for AI later (D144) and stay unused for now.
- **Constraints mirror the domain** (D155): title ≤500 characters, note ≤100 KB, enum checks, subtask depth ≤5 and folder depth ≤3 (trigger functions).

## Sync protocol

1. **Write locally.** Every store action writes to SQLite as it does today, and in the same transaction appends a patch to `sync_outbox`. A patch holds only the changed fields. Creates carry every field.
   - Count-goal check-ins push `{delta}` instead of a value.
   - Detached occurrences use the id `uuidv5(seriesId + originalStart)`.
2. **Push.**
   - The client sends the RPC `sync_push(device_id, client_schema, patches[])`, at most 500 patches and 1 MB per call.
   - The server applies the patches in order inside one transaction. It refuses a patch whose row belongs to someone else, merges the fields (field-level last-writer-wins, in arrival order) and sums deltas.
   - Each touched row is stamped with `version = nextval(...)`.
   - On success the client deletes the pushed outbox rows.
   - When a patch is refused, the reason is logged and the outbox row is dropped, and that one patch is the only data lost. A local "Sync issues" list in Settings → Account shows it.
3. **Pull.**
   - The client sends `sync_pull(cursor)` and gets back the rows with `version > cursor`, including tombstones, ordered by version and paged.
   - Each row is applied locally unless it has pending outbox patches. In that case, the remote fields that aren't pending are applied and the pending local ones are kept, so the push that follows decides the result.
   - The cursor advances.
4. **When sync runs:**
   - on launch and on sign-in;
   - 2 seconds after a local write (debounced);
   - on a Supabase Realtime "changed" ping for this owner;
   - every 5 minutes;
   - when the network comes back.
5. **Version skew:**
   - If `client_schema < min_client_schema`, push is refused and sync stops with "Update Momentum to keep syncing". The existing updater runs.
   - The local app keeps working.
   - The server never drops columns that it knows and the client doesn't.
6. **Tombstones and long absence:**
   - The server keeps tombstones for 90 days.
   - A device whose cursor is older than the oldest kept tombstone downloads everything again.
   - Rows with pending outbox patches are kept and pushed again as new rows with fresh ids.

The sync client is TypeScript: pure merge and patch logic lives in `src/domain/sync.ts` with tests, and the I/O lives in `src/lib/sync/`.

## First sign-in on a device that has data (D118)

1. Take a backup with the existing pre-migration backup path.
2. Pull the account's data into memory, without applying it yet.
3. Merge:
   - The local inbox's tasks move to the account inbox, and the local inbox is deleted.
   - Tags merge by name, ignoring case.
   - Lists, folders and habits with the same name are **not** merged.
4. Push every local row as a create, then apply the pull.
5. Show a summary dialog ("Added 3 lists, 120 tasks, 4 habits to @handle").

This is idempotent: if the merge is interrupted, running it again doesn't duplicate rows, because the ids are stable and creates are upserts.

## Sign out and switching accounts (D119, D124)

- **The sign-out dialog asks:** "Keep a copy on this device" or "Remove from this device".
  - Remove deletes the local data and keeps one automatic backup.
  - Keep stops syncing and records `sync_state.former_account`.
- **Signing in with data from a different account:**
  - When `former_account` is set and differs from the account signing in, the dialog asks "Add this data to @other" or "Remove it". Remove is the default.
  - Signing back in to the *same* account resumes from where the device left off.

## Import and restore (D122)

- **Import:** the existing import gives every row a fresh id and adds the rows. It never replaces anything.
- **Restore backup:**
  - Typing the handle confirms it.
  - The server takes a snapshot first (an RPC that copies the owner's rows into `snapshots`, keeping the last 3).
  - Then every row is tombstoned and the backup is pushed.

## Security and limits

- The app ships only the anon key. RLS is on for every table, and no table uses the service key from the client.
- **Rate limits:** sign-in codes use Supabase's own limits. Each account gets at most 60 `sync_push` calls a minute; pushes past that wait and are retried later.
- **Tests:** a CI job runs a local Supabase (`supabase start`), signs in as two accounts and checks that neither can read or write the other's rows in any table.

## Verification

- **Domain tests:** patch merge, the delta sum, deterministic occurrence ids, the first-sign-in merge, the tombstone purge rule and the settings split.
- **Sync simulation** (`npm run test:sync`, runs nightly in CI):
  - 2–4 simulated clients against a local Supabase run seeded, randomized offline edits, deletes, moves, check-ins and reconnects.
  - Afterwards every client must equal the server.
  - Each failing seed becomes a fixed regression test.
- **Real-app checks:**
  - Two app instances with different identifiers sign in to one account.
  - Edit a task offline on both instances, reconnect, and confirm both fields survived.
  - Sign out with Keep, then sign in to a second account and confirm the prompt appears.

## Acceptance

- Two devices converge within 5 seconds while both are online.
- A day of offline edits on both merges with no lost fields except true same-field clashes.
- Signed-out use is unchanged.
- Every listed edge case has a passing test.
